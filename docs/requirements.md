# pc-cleaner 要件定義書

- 対象プロダクト：`pc-cleaner`（手動選択型ディスク掃除ツール）
- 版：初版（第1〜第3段階を対象範囲とする）
- 参照資料：`docs/roadmap.md`（将来対応リスト。本書「8. 将来拡張要件」の元資料）

---

## 1. 概要・背景・目的

### 1.1 概要

`pc-cleaner` は、Windows を優先しつつ OS 依存を隔離した、手動選択型のディスク掃除ツールである。Rust で実装し、削除は既定でゴミ箱経由とし、「判定支援」を機能の核とする。

### 1.2 背景

一般的なディスク掃除ツールは、削除候補の一覧を提示するだけで「これは不要か否か」の判定をユーザーに丸投げしがちである。その結果、ユーザーは判断できずにツールを使わなくなる（死にツール化）か、逆に無差別に削除して事故を起こす。本ツールはこの二つの失敗を同時に回避することを目的とする。

### 1.3 設計目標（要件としての言語化）

| ID | 設計目標 | 要件 |
|----|----------|------|
| G1 | 死にツール化を防ぐ | 各削除候補に「何を・なぜ・どれだけ削除するのか」を必ず付与し、判定をユーザーに丸投げしないこと |
| G2 | 誤削除を防ぐ | 削除はゴミ箱経由を既定とし、ドライランを既定とし、対象は許可リスト方式に限定すること |
| G3 | OS 依存を閉じ込める | OS 固有の知識を `Platform` trait で抽象化し、固有実装を 1 ファイルに隔離すること |
| G4 | CLI/GUI で挙動を共有する | ロジックを `core` に集約し、UI は表示と操作のみを担うこと。CLI と GUI で同一入力に対し同一結果となること |
| G5 | 将来拡張に耐える | 管理者権限領域および他 OS への対応を、`Platform` trait と `Config` の構造を変えずに後付けできること |

### 1.4 目的

ユーザーが「白紙から選ぶ」のではなく「ツールの推奨をレビューして微調整する」立場になれる状態を実現すること。

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| Rule | 掃除ルール。許可リストの 1 項目であり、判定支援の一次情報。走査の基点・絞り込み条件・安全度・説明文などを保持する |
| ScanEntry | 走査結果として得られた削除候補エントリ。パス・サイズ・件数・更新日時・経過日数・推奨可否・理由・選択状態を保持する |
| Safety | ルールの安全度区分。`Safe` / `Caution` / `Review` の 3 値をとり、既定の選択状態と表示方法を決定する |
| KnownDir | OS 固有の実パスを直接書かずに走査基点を指定するための抽象キー。`UserTemp` / `SystemTemp` / `LocalAppData` / `Cache` / `RecycleBin` / `Downloads` を持つ |
| Platform trait | OS 固有の知識（既知ディレクトリ解決・ゴミ箱送り・管理者権限要否判定）を隠蔽する抽象インターフェース |
| MatchKind | ルール内での対象絞り込み方式。`All` / `Extension(Vec<String>)` / `OlderThan` を持つ |
| recommend | `ScanEntry` と `Rule` を入力として推奨可否と理由を返す純粋関数 |
| Recommendation | `recommend` の戻り値。推奨可否（`recommended`）と理由文（`reason`）を持つ |
| Config | ユーザー設定。ルール毎の既定、ゴミ箱利用可否、ドライラン既定を保持し永続化される |
| RulePref | ルール毎のユーザー既定（常に選択 / 除外 / 毎回確認） |
| ドライラン | 削除を行わず、削除予定の内容と解放見込み容量のみを提示する動作モード |
| 許可リスト方式 | 明示的に定義されたルールに合致するもののみを削除候補とし、それ以外は一切対象としない方式 |

## 3. スコープ

### 3.1 初版でやること

- `core` ライブラリ crate（rule / entry / scan / recommend / delete / config / platform）の実装
- Windows 向けの `Platform` 実装（既知ディレクトリ解決、ゴミ箱送り、管理者権限要否判定）
- 判定支援ロジック（安全度による既定選択、メタ情報付与、`recommend()` による推奨の動的補正）
- ゴミ箱経由の削除実行、およびドライラン
- ユーザー設定の保存・読込
- 薄い CLI（`scan` / `clean --dry-run` / `clean` / `--permanent`）
- egui による GUI（チェックボックス一覧・容量表示・設定保存）
- 初期ルールセット（`user_temp` / `browser_cache` / `thumbnail_cache` / `recycle_bin` / `old_logs` / `old_downloads`）

### 3.2 初版でやらないこと

以下は初版スコープ外とし、構造のみ用意して有効化は後日とすること。詳細は「8. 将来拡張要件」に従う。

- 管理者権限を要する領域の実際の走査・削除（`needs_admin = true` のルールはフィルタで除外すること）
- 権限昇格フロー（UAC 昇格、昇格プロセスへの委譲）
- macOS / Linux 向けの `Platform` 実装（`platform/unknown.rs` の最小スタブのみ用意する）
- 経過日数しきい値のユーザー調整 UI（初版はルールにハードコードすること）
- 削除ログの記録、ドライラン結果のエクスポート、ロールバック補助
- ルール定義の外部ファイル化
- 定期実行 / スケジューラ連携、多言語対応

### 3.3 境界の明確化

初版でやらない項目は、いずれも `Platform` trait または `Config` の構造をそのまま活かして後付けできる形でなければならない。初版の実装が将来対応のために構造変更を強いる状態になってはならない。

## 4. システム構成要件

### 4.1 ワークスペース構成

Cargo workspace として以下の構成を採ること。

```
pc-cleaner/
├── Cargo.toml            # workspace定義
├── core/                 # ライブラリcrate：ロジック本体（UI非依存）
│   ├── rule.rs               # 掃除ルール（許可リスト）
│   ├── entry.rs              # 削除候補エントリ
│   ├── scan.rs               # 走査・容量集計
│   ├── recommend.rs          # 推奨ヒューリスティック（純粋関数）
│   ├── delete.rs             # 削除実行（ゴミ箱/ドライラン）
│   ├── config.rs             # ユーザー設定の保存/読込
│   └── platform/
│       ├── mod.rs            # trait Platform（OS非依存の抽象）
│       ├── windows.rs        # #[cfg(windows)] 実装をここに隔離
│       └── unknown.rs        # 他OS用スタブ（当面最小）
├── cli/                  # バイナリcrate：薄いCLI（検証・自動化用）
└── gui/                  # バイナリcrate：egui（手動選択用、後で追加）
```

- `core` は OS 固有 API を直接呼び出してはならない。
- `cli` と `gui` は `core` を共有すること。CLI で固めた挙動がそのまま GUI に乗る状態を維持すること。
- `gui` crate は第3段階で追加すること。

### 4.2 Platform trait による OS 分離方針

- OS 固有の知識は `Platform` trait の裏に閉じ込めること。
- `Platform` trait は次の 5 つの責務を持つこと：既知ディレクトリの解決（`known_dir(KnownDir) -> Option<PathBuf>`）、ゴミ箱送り（`to_trash(&Path) -> Result<()>`）、管理者権限要否の判定（`requires_admin(&Path) -> bool`）、昇格状態の判定（`is_elevated() -> bool`）、権限昇格の実行（`elevate(&[String]) -> ElevateResult`。5.8 参照、A2 / Issue #41）。
- `KnownDir` は `UserTemp`（`%TEMP%`）、`SystemTemp`（`C:\Windows\Temp`、要管理者。A1 / Issue #40 で有効化済み）、`LocalAppData`（`%LOCALAPPDATA%`）、`Cache`（各種キャッシュ基点）、`RecycleBin`、`Downloads`（`%USERPROFILE%\Downloads`）、`WindowsUpdateCache`（`%SystemRoot%\SoftwareDistribution\Download`、要管理者。A3 / Issue #42）、`DeliveryOptimizationCache`（`%SystemRoot%\ServiceProfiles\NetworkService\AppData\Local\Microsoft\Windows\DeliveryOptimization\Cache`、要管理者。A4 / Issue #43）を持つこと。
- ルール定義に `C:\Windows\Temp` のような生パスを記述してはならない。必ず `KnownDir` の抽象キーで記述すること。
- `#[cfg(windows)]` は `platform/windows.rs` の中にだけ登場させ、他のファイルへ漏らしてはならない。
- `platform/windows.rs` に入れてよいのはパス解決とゴミ箱送りのみとし、ルールとロジックは OS 非依存のまま保つこと。
- ゴミ箱送りには `trash` クレートを用いること。同クレートはクロスプラットフォーム対応であるため `to_trash` の実装は薄く保つこと。

## 5. 機能要件

### 5.1 走査機能（scan）

| ID | 要件 |
|----|------|
| F-SCAN-01 | 有効なルールの `base`（`KnownDir`）を `Platform::known_dir` で実パスへ解決し、そのパス配下を走査すること |
| F-SCAN-02 | ルールの `match_kind` に従い対象を絞り込むこと（`All` は全件、`Extension` は指定拡張子、`OlderThan` は `age_threshold_days` と併用した経過日数判定） |
| F-SCAN-03 | 走査結果は `ScanEntry` として保持し、少なくとも由来ルール ID・パス・サイズ・ファイル数・最終更新日時・経過日数（`age_days`）を集計すること |
| F-SCAN-04 | `needs_admin = true` のルールは、昇格していない場合は走査対象からフィルタ除外すること。昇格している場合（A1 / Issue #40）は対象に含めること |
| F-SCAN-05 | 走査は基点ごとに並列実行できること。長時間となる走査については進捗を通知できること |
| F-SCAN-06 | ワンクリック掃除の動線では、Safe ルールの基点だけを走査対象とできること |
| F-SCAN-07 | 手動レビューの動線では、Safe / Caution / Review のすべてのルールを走査し、各エントリにメタ情報を付与すること |
| F-SCAN-08 | 走査は許可リスト方式であり、定義されたルールに合致しないファイル・ディレクトリを候補に含めてはならない |

### 5.2 判定支援機能（recommend）

判定支援は以下の 4 段構えで構成すること。

| ID | 要件 |
|----|------|
| F-REC-01 | ルールが理由を語ること。各候補に対しルールの `description` と `safety` を判断材料として提示すること |
| F-REC-02 | 安全度で既定選択を決定すること。`Safe` は既定 ON、`Caution` / `Review` は既定 OFF とすること。起動直後に「Safe だけ選択済み」の状態が成立し、ワンクリック掃除が可能であること |
| F-REC-03 | メタ情報を付与すること。最終更新日時・総容量・ファイル数・由来ルール・経過日数を一覧に表示すること |
| F-REC-04 | 推奨を動的に補正すること。`recommend(entry, rule) -> Recommendation` により状況に応じて推奨可否を上書きし、その理由を `reason` に格納すること |
| F-REC-05 | `recommend` は純粋関数として実装し、単体テスト可能かつ CLI / GUI 共通で同一に作用すること |
| F-REC-06 | 補正の例として、使用中の可能性がある Temp（更新が数分前）は推奨から外すこと、180 日以上経過したログは推奨 ON 寄りに補正することを満たすこと |
| F-REC-07 | 推奨判定は「安全度 × 経過日数 × 使用中の可能性」の組み合わせでエントリごとに行うこと |
| F-REC-08 | ユーザーが個別ファイルを開いて調べなくても判断できるだけの情報（`description` と `safety`、および `age_days` と `reason`）を必ず提示すること |

#### 5.2.1 Safety 区分と既定

| Safety | 内容 | 既定 |
|--------|------|------|
| `Safe` | 再生成される一時領域・キャッシュ | チェック ON |
| `Caution` | 状況次第（古い DL、大きなログ） | OFF・注意色 |
| `Review` | 中身の確認が必要 | OFF・確認前提 |

- `Caution` は注意色で表示すること。
- `Review` はユーザーが中身を開いて確認する前提とし、既定で選択してはならない。

### 5.3 削除実行機能（delete）

| ID | 要件 |
|----|------|
| F-DEL-01 | 削除は必ず「走査 → プレビュー → 実行」の 3 段を通すこと。この順序を省略できる経路を設けてはならない |
| F-DEL-02 | 実行時の既定は `use_trash = true` とし、`trash` クレートによりゴミ箱へ送ること。誤りが復旧可能であること |
| F-DEL-03 | 削除対象は許可リスト（ルール）に合致し、かつユーザーが選択した（`selected = true`）エントリのみとすること |
| F-DEL-04 | プレビュー時に、選択分の解放見込み容量を再集計して提示すること |
| F-DEL-05 | ドライランでは実際の削除を一切行わないこと |
| F-DEL-06 | 完全削除（ゴミ箱を経由しない削除）は、明示オプションが指定されたときのみ実行すること。復旧不可であるため確認を要すること |

- `recycle_bin` ルール由来のエントリ（走査対象が既にゴミ箱の中にある）は `Platform::to_trash` の対象にしない。完全削除（`--permanent` 明示時のみ）でのみ実行し、コンテナ（SID ディレクトリ）自体は残して中身だけを恒久削除する（Issue #17 実装時に決定）。
- `use_trash = false` は完全削除への自動昇格を意味しない。ゴミ箱送りが実行できない状態として扱い、理由付きでドライランへフォールバックする。完全削除は F-DEL-06 の明示オプション経由のみで発生させること（Issue #7 実装時に解釈を確定）。

### 5.4 設定の保存・読込（config）

| ID | 要件 |
|----|------|
| F-CFG-01 | 設定として `rule_prefs`（ルール毎の既定：常に選択 / 除外 / 毎回確認）、`use_trash`、`dry_run_default` を保持すること |
| F-CFG-02 | `use_trash` の既定値は `true` とすること |
| F-CFG-03 | `dry_run_default` の既定値は `true` とすること |
| F-CFG-04 | 設定は `%APPDATA%\pc-cleaner\config.json` 等に永続化し、2 回目以降の起動で即実行できる状態を復元すること |
| F-CFG-05 | 起動時に設定ファイルを読み込み、前回の `rule_prefs` と `use_trash` を復元すること。設定ファイルが存在しない場合は既定値で動作すること |

### 5.5 CLI 要件

| ID | 要件 |
|----|------|
| F-CLI-01 | CLI は薄い実装とし、検証・自動化用途に用いること。ロジックは `core` に置き CLI 側に重複させないこと |
| F-CLI-02 | `scan` サブコマンドは走査結果の一覧を出力し、削除を行わないこと |
| F-CLI-03 | `clean --dry-run` は削除予定のプレビューを出力し、削除を行わないこと |
| F-CLI-04 | `clean` は明示実行としてゴミ箱削除を実行すること |
| F-CLI-05 | `--permanent` オプション指定時のみ完全削除を行うこと |
| F-CLI-06 | CLI は明示的に解除しない限り削除を行わないこと（`dry_run` が既定的挙動であること） |
| F-CLI-07 | 一覧出力には、ルール・パス・サイズ・`age_days`・推奨可否・合計解放見込みを含め、標準出力へ出力すること |
| F-CLI-08 | CLI と GUI で走査・推奨の結果が一致すること |

### 5.6 GUI 要件

GUI は第3段階の成果物とし、egui を用いて実装すること。

| ID | 要件 |
|----|------|
| F-GUI-01 | 削除候補をチェックボックス一覧として表示すること |
| F-GUI-02 | 各行に、サイズ・`age_days`・由来ルール・`reason` を表示すること |
| F-GUI-03 | 安全度に応じた表示区別（`Caution` の注意色等）を行うこと |
| F-GUI-04 | 起動直後は `Safe` のエントリが選択済みであり、そのまま確定して実行できること |
| F-GUI-05 | 選択の増減に追随して解放見込み容量を表示・再集計すること |
| F-GUI-06 | ユーザーの設定（`rule_prefs` 等）を保存できること |
| F-GUI-07 | GUI は表示と操作のみを担い、判定・削除のロジックを持たないこと |

### 5.7 初期ルールセット

初版では、確実に安全で効果が見える定番のみを実装すること。まず `Safe` で固め、`Caution` 以降は後付けとする。

| id | 対象 | 基点（KnownDir） | Safety | 初版での扱い |
|----|------|------------------|--------|--------------|
| `user_temp` | ユーザー一時ファイル | `UserTemp` | Safe | 有効 |
| `browser_cache` | ブラウザ/アプリのキャッシュ | `Cache` | Safe | 有効 |
| `thumbnail_cache` | サムネイルキャッシュ | `LocalAppData` | Safe | 有効 |
| `recycle_bin` | ゴミ箱 | `RecycleBin` | Caution | 有効（既定 OFF） |
| `old_logs` | 古いログ（180 日超） | `LocalAppData` | Caution | 有効（既定 OFF） |
| `old_downloads` | 古いダウンロード（90 日超） | `Downloads` | Review | 有効（既定 OFF・確認前提） |
| `system_temp` | `C:\Windows\Temp` | `SystemTemp` | Review（要管理者） | `needs_admin = true`。昇格していない場合のみフィルタ除外（A1 / Issue #40） |
| `windows_update_cache` | Windows Update のダウンロード済みファイル | `WindowsUpdateCache` | Review（要管理者） | `needs_admin = true`。昇格していない場合のみフィルタ除外（A3 / Issue #42）。基点は `SoftwareDistribution\Download` に限定し、更新履歴データベース（`DataStore`）は対象にしない |
| `delivery_optimization_cache` | 配信の最適化ファイル | `DeliveryOptimizationCache` | Review（要管理者） | `needs_admin = true`。昇格していない場合のみフィルタ除外（A4 / Issue #43）。`DOModifyCacheDrive` でキャッシュ位置を変更している環境では走査結果が0件になる（既知の制約） |

- `old_logs` の経過日数しきい値は 180 日、`old_downloads` は 90 日とし、初版ではルールにハードコードすること。ただし将来 `Config` へ移せる構造とすること。
- 各ルールは安定した識別子（`id`）、表示名（`label`）、説明文（`description`）を必ず持つこと。
- `recycle_bin` は当初 Safe（既定 ON）としていたが、設計目標 G2「削除はゴミ箱経由を既定とし、誤りが復旧可能であること」と衝突するため Caution（既定 OFF）に変更した（Issue #9 実装時に判断）。ゴミ箱の中身を消す操作にはゴミ箱という退避先が存在せず、Safe のままではワンクリック掃除（フロー①）が確認 1 回でゴミ箱を完全に空にしてしまうため。

### 5.8 権限昇格（elevate）

将来対応 A2（Issue #41）で追加。管理者権限が必要な領域（8.1）を対象にするための昇格フローを定める。方式は「UAC 昇格 or 昇格プロセスへの委譲」のうち、**プロセス全体を `runas` で起動し直し、元の非昇格プロセスは終了する**方式を採用する（子プロセスへの処理委譲は採らない）。

| ID | 要件 |
|----|------|
| F-ELV-01 | 管理者権限領域を対象にする要求があり、かつ未昇格の場合、UAC を経由して自プロセスを管理者権限で起動し直し、元のプロセスは終了すること |
| F-ELV-02 | 昇格の有無はプロセストークンの `TokenElevation` により判定すること（`IsUserAnAdmin` 等のグループ所属判定は使わないこと。UAC で分割されたトークンを取り違えると再昇格ループに直結するため） |
| F-ELV-03 | 昇格後プロセスには再昇格を抑止する内部マーカーを渡し、無限に再昇格し続けないこと |
| F-ELV-04 | UAC のキャンセルは通常の失敗と区別して扱い、専用の終了コード（CLI では `2`）で報告すること |
| F-ELV-05 | 昇格の実行（`Platform::elevate`）は起動の成否のみを返し、`process::exit` の判断は CLI/GUI 側が行うこと（`core` はプロセスを終了させない） |

- 昇格状態を走査・削除の対象化に接続する部分（`needs_admin` ルールを実際に対象化する）は A1（Issue #40）で対応済み。7.4 参照。

## 7. 処理フロー要件

削除に至る基本の流れは「走査 → 判定支援 → プレビュー → ゴミ箱削除」の 4 段とし、以下の 4 パターンを満たすこと。

### 7.1 フロー①：ワンクリック掃除（Safe のみ・最短動線）

何も考えずに安全なファイルだけ掃除したいケース。起動直後の既定状態がそのまま実行できること。

| # | ステップ | 担当 | 要件 |
|---|----------|------|------|
| 1 | 起動・設定読込 | `config.rs` | 設定ファイル（`%APPDATA%` 配下の `config.json`）を読み、前回の `rule_prefs` と `use_trash = true` を復元すること |
| 2 | プラットフォーム解決 | `platform/windows.rs` | `KnownDir` の抽象キーを実パスへ解決すること。`needs_admin = true` のルールは当面フィルタ除外すること |
| 3 | 走査・集計 | `scan.rs` | Safe ルールの基点だけを並列走査し、サイズ・件数・更新日時・`age_days` を集計し、進捗を通知すること |
| 4 | 既定選択 | 判定支援 | 安全度 `Safe` のエントリを自動で `selected = ON` とすること。ユーザーは確認するだけでよいこと |
| 5 | プレビュー → 実行 | `delete.rs` | 解放容量を提示し、確定操作で `to_trash()` によりゴミ箱送りすること。誤りは復旧可能であること |

- 本フローにおけるユーザーの意思決定は「確定」の 1 回だけであること。

### 7.2 フロー②：手動レビュー（Caution / Review を吟味）

既定 OFF の候補を、判断材料を見ながら選ぶケース。判定支援ロジックの主戦場である。

| # | ステップ | 担当 | 要件 |
|---|----------|------|------|
| 1 | 全ルール走査 | `scan.rs` | Safe / Caution / Review すべてを走査し、各エントリにメタ情報を付与すること |
| 2 | 推奨の動的補正 | `recommend.rs` | 純粋関数 `recommend(entry, rule)` により推奨を状況で上書きし、理由を `reason` に格納すること |
| 3 | 推奨の判定（分岐） | 判定支援 | 「安全度 × 経過日数 × 使用中の可能性」でエントリごとに推奨を判定すること |
| 3a | 分岐：Safe | — | 既定 ON とし、`reason` に「再生成される一時領域」の旨を設定すること |
| 3b | 分岐：Caution | — | 180 日超のログは推奨 ON 寄りに補正し、注意色で表示すること |
| 3c | 分岐：Review | — | 既定 OFF とし、ユーザーが中身を開いて確認する前提とすること |
| 4 | ユーザーが微調整 | GUI | サイズ・`age_days`・由来ルール・`reason` を見て選択を増減できること。白紙からの選択にしないこと |
| 5 | プレビュー → ゴミ箱削除 | `delete.rs` | 選択分の解放容量を再集計し、確定でゴミ箱送りすること |

### 7.3 フロー③：ドライラン（CLI・自動化 / 消さずに確認）

薄い CLI で挙動を検証、または定期実行で「何が消える予定か」だけを見るケース。本フロー内で削除が起きてはならない。

| # | ステップ | 要件 |
|---|----------|------|
| 1 | 起動 | `pc-cleaner scan` または `pc-cleaner clean --dry-run` を受け付けること。CLI は明示解除しない限り削除しないこと（`dry_run` が既定的挙動） |
| 2 | 走査＋推奨 | GUI と同一の `core`（`scan` / `recommend`）を用い、CLI/GUI で結果が一致すること |
| 3 | 一覧出力（削除なし） | ルール・パス・サイズ・`age_days`・推奨可否・合計解放見込みを標準出力へ出力すること |
| 4a | 分岐：明示実行 | `pc-cleaner clean` によりゴミ箱削除を実行すること |
| 4b | 分岐：完全削除 | `--permanent` が明示指定されたときのみ完全削除すること。復旧不可のため確認を要すること |

### 7.4 フロー④：管理者権限領域（A1 / A2 対応済み）

初版スコープ外だったが、A2（Issue #41）・A1（Issue #40）で対応済み。構造は変えていない（NF-EXT-01）。

| # | ステップ | 要件 |
|---|----------|------|
| 1 | 走査時に権限判定 | `Platform::requires_admin()` により権限要否を判定すること。`C:\Windows\Temp` 等は `needs_admin = true` とすること |
| 2 | 分岐条件 | 昇格権限を持っているかを判定すること（A2 / Issue #41：`Platform::is_elevated()` として実装済み） |
| 2a | 未昇格：除外 | 候補から外し、一覧に「管理者権限が必要」と表示して事故を防ぐこと |
| 2b | 昇格済み：対象化 | `Rule::is_permitted` / `Rule::may_touch_admin_area` を経由して `needs_admin` ルールを対象化すること（A1 / Issue #40、対応済み）。この対応で `Platform` trait・`Config` の構造は変えていない |

- 同じ仕組みで他 OS（macOS / Linux）の `platform` 実装も追加できること。

## 9. 受け入れ基準／完了の定義

### 9.1 実装段階と成果物

| 段階 | 内容 | 成果 |
|------|------|------|
| 第1段階 | workspace ＋ `core`（rule/entry/scan/recommend/delete/config/platform） | ロジック本体 |
| 第2段階 | 薄い CLI（`scan` 一覧 / `clean --dry-run` プレビュー / `clean` ゴミ箱削除） | 動く実用ツール |
| 第3段階 | egui GUI（チェックボックス一覧・容量表示・設定保存） | 手動選択 UI |

### 9.2 第1段階の完了条件

- workspace が定義され、`core` が単独でビルドできること。
- `Rule` / `ScanEntry` / `Safety` / `MatchKind` / `KnownDir` / `Config` / `RulePref` / `Recommendation` が定義されていること。
- `Platform` trait と Windows 実装、他 OS スタブが存在し、`#[cfg(windows)]` が `platform/windows.rs` の外に出ていないこと。
- 初期ルールのうち Safe/Caution/Review の各ルールが定義され、`system_temp` は `needs_admin = true` としてフィルタ除外されること。
- 走査が `ScanEntry`（サイズ・件数・更新日時・`age_days`）を返すこと。
- `recommend()` が純粋関数として実装され、単体テストで検証できること（少なくとも「更新が数分前の Temp は非推奨」「180 日超のログは推奨 ON 寄り」の 2 ケース）。
- 削除がゴミ箱経由（`use_trash = true`）とドライランの両方に対応すること。
- 設定の保存・読込が動作し、既定値が `use_trash = true` / `dry_run_default = true` であること。

### 9.3 第2段階の完了条件

- `scan` / `clean --dry-run` / `clean` / `--permanent` が動作すること。
- 明示的な指定がない限り削除が発生しないこと。
- 一覧出力にルール・パス・サイズ・`age_days`・推奨可否・合計解放見込みが含まれること。
- フロー③のステップが一通り実行できること。
- ロジックが CLI 側に重複していないこと。

### 9.4 第3段階の完了条件

- チェックボックス一覧が表示され、サイズ・`age_days`・由来ルール・`reason` が確認できること。
- 起動直後に Safe が選択済みで、確定操作のみでフロー①が完遂できること。
- Caution / Review を含む一覧上でフロー②の微調整と再集計が行えること。
- 設定（`rule_prefs` 等）が保存され、次回起動で復元されること。
- GUI に判定・削除ロジックが含まれていないこと。

### 9.5 全段階共通の完了条件

- 同一環境・同一設定において、CLI と GUI の走査結果および推奨結果が一致すること。
- 「走査 → プレビュー → 実行」を経由しない削除経路が存在しないこと。
- `needs_admin = true` の領域に対する削除は、昇格していない状態では発生しないこと（A1 / Issue #40 以降は、昇格済みかつユーザーが明示的に選択した場合のみ発生しうる）。
